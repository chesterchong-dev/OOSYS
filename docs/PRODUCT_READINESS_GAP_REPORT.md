## Executive decision

OOSYS is a foundation-stage software project, not a complete enterprise product and not yet ready for commercial release. Phases 00–04 are accepted only for their recorded scoped milestones. Phase 05 has repository-level security/observability controls; baseline SHA `b5d4a3c6bc5d9604437bd00483c2063ac4d51047` passed all three PR workflows: Phase 00 validation [39963373191](https://github.com/chesterchong-dev/OOSYS/actions/runs/39963373191), Dependency Audit [39963373277](https://github.com/chesterchong-dev/OOSYS/actions/runs/39963373277), and Secret Scan [39963373227](https://github.com/chesterchong-dev/OOSYS/actions/runs/39963373227). Those runs establish repository CI only; they do not establish production deployment or operational acceptance. Any code change after this baseline requires new exact-head CI.

The register contains 87 stable requirement IDs: 13 marked `partial`, 74 marked `missing`. These are broad product requirement statuses, not a count of all phase acceptance milestones. The accepted identity, API/readiness and UI-shell work is a reusable foundation, but core business modules and production operations remain substantially unimplemented.

## Current Phase 05 implementation and next actions

### Verified at baseline

- Structured JSON request logging and request ID normalization/propagation; query strings, headers and bodies are excluded from the log payload.
- Baseline security response headers and explicit-origin CORS using bearer authentication.
- Production rate-limit secret validation; optional token-protected process-local metrics, disabled by default.
- Existing database-backed login rate limiting; tests for recovery/invitation misuse and session revocation.
- GitHub Actions coverage for backend/frontend tests/build, migration and disposable PostgreSQL restore checks, dependency audit and repository-history secret scan.
- All three workflows passed on the audit baseline SHA above.

### Genuine repository-level improvement identified

The CORS validator rejects wildcard and path-bearing origins but its string check can allow query/fragment/user-info forms that are not valid serialized origins. Tighten parsing to require an HTTP(S) scheme, a valid hostname/port, no credentials, no path, no query and no fragment; add regression tests. This is an in-scope configuration validation fix, not a change to the API or authentication contract. The fix requires exact-head CI before it is considered verified.

### Remaining Phase 05 operational gaps

- **OOSYS-CORE-012:** process-local metrics are not a central monitoring system. No central collector, alert routes or missing-telemetry watchdog are evidenced.
- **OOSYS-CORE-014:** CI restore uses disposable synthetic data. Production backup encryption, retention, off-site isolation, least-privilege access and measured RPO/RTO are unverified.
- **OOSYS-CORE-015:** no authorized independent penetration test, remediation/retest or residual-risk sign-off is evidenced.
- **OOSYS-OPS-085:** no named on-call destination, end-to-end alert lifecycle or timed operational recovery rehearsal is evidenced.
- **OOSYS-OPS-087:** no staging promotion, immutable artifact provenance, production approval or executed rollback rehearsal is evidenced.

Keep all five requirements partial. Proposed RPO ≤15 minutes and RTO ≤4 hours are not approved commitments or measured service guarantees.

## Cross-cutting product gaps

### Core architecture and data

- Continue the modular monolith with explicit module ownership, dependency injection, versioned API contracts and separate routing/application/domain/repository/persistence/infrastructure responsibilities.
- For every business entity, implement validated CRUD and lifecycle operations, bounded pagination/filtering, permissions, tenant isolation, audit history, migrations, indexes and tests. Prefer archive/soft-delete or controlled reversal when financial/inventory history must remain auditable.
- For every tenant-owned record and background job, prove server-side tenant filtering and cross-tenant denial; add PostgreSQL RLS/constraints where appropriate. Phase 02 coverage only applies to implemented identity-owned data, not future module tables.
- Use decimal arithmetic and explicit currency/rounding policies for accounting, pricing, payroll and inventory valuation.
- Define stable integration events, idempotency, retries, outbox/replay semantics and versioning before cross-module automation depends on them.

### GUI and customer workflows

- **GUI status:** a React/TypeScript/Vite/Tailwind frontend shell and limited administration UI exist under the scoped Phase 04 milestone. The full product UI is not complete.
- Required shared UX includes responsive navigation, accessible forms/tables/filters/dialogs, validation, loading/empty/error/retry states, role-aware dashboards, audit/activity timelines, import/export progress and consistent permissions on every drill-down.
- A module is customer-testable only after a real vertical slice works end-to-end: create/read/update/archive, authorization, tenant boundaries, persistence, audit, validation/failure states, UI flow, migration, integration tests and a seeded demo scenario. A page or mockup alone is not a working module.
- The first vertical slice should be a deliberately limited customer workflow chosen by the product owner, not a broad attempt to implement every ERP feature simultaneously.

### SaaS and private deployment

- **SaaS:** tenant onboarding/provisioning/suspension/export/deletion; enforced entitlements and usage limits; billing adapter and subscription lifecycle; tenant-safe file storage; central secrets/configuration; data residency/retention; observability, backups, restore and incident response.
- **Private deployment:** supported deployment package, versioned configuration, secrets integration, upgrade/migration path, supported database/runtime matrix, offline/limited-connectivity strategy where required, diagnostics, backup/restore and customer-operated upgrade/rollback documentation.
- **Shared requirements:** migration compatibility, tenant isolation, audit, identity/permissions, monitoring, release provenance and repeatable installation. Private deployment does not mean skipping the same security or upgrade gates.
- Do not choose a cloud, database hosting, billing, metrics, email, WhatsApp, object storage or private-install provider without the product/platform owner deciding the target and operating model.

### Commercial and operational launch

Before charging customers, define target segment and initial module scope; subscription tiers/entitlements; billing and failed-payment handling; onboarding/data migration; support channels and response targets; SLA/status communications; incident and breach response; backup/retention/deletion; privacy/data processing terms; licensing and third-party notices; vulnerability disclosure and patch policy; service ownership; cost/unit economics; customer acceptance/UAT; training/docs; release/rollback and support escalation. Obtain legal/privacy review for intended launch jurisdictions and data classes. None of these should be treated as satisfied merely because CI passes.

## Priority sequence from repository to release

1. **Close Phase 05 repository acceptance:** tighten CORS origin parsing; add tests; pass all workflows on the new exact head; reconcile PR text. Keep the PR draft while operational evidence remains open.
2. **Make Phase 05 operationally real:** product/platform/security/release owners choose providers and operating policies; provision isolated staging and backup/monitoring; run alert lifecycle, restore, penetration-test remediation/retest and rollback rehearsals; record sanitized evidence and approvals.
3. **Freeze core contracts:** confirm tenant, permission, audit, error, API versioning, event/outbox, file and settings contracts. Review compatibility with accepted phases before shared schema changes.
4. **Complete shared platform foundations:** settings, files, notifications, search, integration adapter framework, subscription/entitlement, audit usability, monitoring and release automation, each with real persistence/API/UI/tests and tenant isolation.
5. **Build one customer-facing vertical slice:** choose an initial target industry and one workflow spanning core master data, inventory/sales or another chosen module, role permissions, UI, reporting and integration. Run customer UAT with representative data and failure cases.
6. **Expand modules in dependency order:** inventory/stock ledger → warehouse → purchasing → customers/quotations/orders/CRM → finance/accounting → projects → HR/payroll → engineering/PLM → manufacturing → quality/assets/service → communications/integrations → AI/search/reporting → offline/private deployment and industry packs. Keep the phase roadmap authoritative and update statuses only with evidence.
7. **Release readiness:** staging soak and load tests; tenant-isolation and authorization test suite; independent security review; migration/rollback and restore drills; observability/on-call; privacy/licensing/legal checks; support runbooks; pricing/billing/entitlements; customer UAT; documented go/no-go by authorized owners.
